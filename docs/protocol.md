# Device protocol

Protocol version 1 is a little-endian, framed request/response protocol carried on the Pico 2 CDC configuration interface at 115200 8N1. The same commands are available while the class-compliant USB-MIDI interface is active; MIDI traffic is independent of configuration frames.

## Frame layout

Every frame is:

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | ASCII magic `MPCF` |
| 4 | 2 | protocol version (`u16`, `1`) |
| 6 | 4 | request id (`u32`) |
| 10 | 2 | command (`u16`) |
| 12 | 2 | flags (`u16`, currently zero) |
| 14 | 4 | payload length (`u32`, maximum 4096) |
| 18 | n | payload |
| 18+n | 4 | CRC-32/IEEE over bytes 0 through 17+n |

The decoder accepts arbitrary serial chunk boundaries, ignores noise before the next magic value, and continues after a CRC error. A request id is generated by the editor and is reused for every retry. Firmware caches the latest response for each request id, making retries idempotent.

The host waits 1000 ms for a response and makes three total attempts. A response uses the same frame shape; its payload begins with a status code and command-specific result. The error codes are `CRC_MISMATCH`, `UNSUPPORTED_VERSION`, `PAYLOAD_TOO_LARGE`, `UNKNOWN_COMMAND`, `INVALID_FRAME`, `INCOMPATIBLE_DEVICE`, `INVALID_CONFIGURATION`, `INVALID_STATE`, `VERIFY_FAILED`, and `BUSY`.

## Commands

| Value | Command | Payload |
| ---: | --- | --- |
| 1 | `GET_CAPABILITIES` | empty |
| 2 | `GET_CONFIG_INFO` | empty |
| 3 | `READ_CONFIG` | bank index `u8` (0–127) |
| 4 | `BEGIN_UPLOAD` | image size `u32`, image sequence `u32`, image CRC-32 `u32` |
| 5 | `WRITE_CHUNK` | offset `u32` followed by up to 1024 image bytes |
| 6 | `VERIFY_UPLOAD` | empty |
| 7 | `ACTIVATE_UPLOAD` | empty |
| 8 | `GET_EXPRESSION_SAMPLE` | empty |
| 9 | `SET_EXPRESSION_CALIBRATION` | heel ADC `u16`, toe ADC `u16` |
| 10 | `FACTORY_EMPTY_RESET` | empty |

`GET_CAPABILITIES` reports the device model, firmware version, protocol version, config schema, image format, queue capacity, supported destinations, and expression/relay/display capabilities. `GET_CONFIG_INFO` reports the active image sequence, length, CRC, and active slot. `READ_CONFIG` returns the requested bank record from the active validated image.

## Synchronization lifecycle

1. Query capabilities and config metadata.
2. Validate the complete local JSON document and compile one binary image.
3. Send `BEGIN_UPLOAD` with image size, sequence, and CRC.
4. Send contiguous `WRITE_CHUNK` requests, each no larger than 1024 bytes.
5. Send `VERIFY_UPLOAD`; firmware validates the inactive slot and reads it back.
6. Send `ACTIVATE_UPLOAD`; firmware advances the active marker only after verification.
7. Query `GET_CONFIG_INFO` and compare the active sequence, length, and CRC with the compiled image.

Power loss, disconnect, malformed data, a missing chunk, or failed CRC leaves the previous active image selected. The editor reports that previous configuration as intact and may reconnect and retry. `FACTORY_EMPTY_RESET` writes and activates the checked-in empty image; it never changes firmware.

## Expression calibration

The editor requests a live sample, asks the user to move the pedal to heel and toe, and sends the two measured ADC endpoints. Firmware rejects a span below 410 counts, stores the accepted endpoints in controller-level settings, and reports the result. Invalid or disconnected expression input emits no MIDI.

## Compatibility

A device must reject unsupported protocol versions, config schemas, image formats, and device models before reading or mutating configuration. Adding optional response fields is compatible; changing byte order, field meaning, command lifecycle, or safety behavior requires a protocol or image-format version bump and a compatibility entry in the release manifest.
